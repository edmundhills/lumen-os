# tests

Tests that cover more than one component, and the checks for the developer setup. Unit tests live next to the code they test (`cargo test`, Qt Test).

The other layers (session, glass visual, accessibility, performance, update and Windows compatibility tests) get their folders when their steps start.

## How the ISO's boot test works

- **The VM** is QEMU's q35 machine with 4 CPUs and 6 GiB, using KVM, with the ISO in its CD drive and no network. Its firmware is Fedora's OVMF build with Secure Boot on and Microsoft's keys enrolled, found through the firmware descriptors edk2-ovmf installs, as libvirt finds it, with SMM guarding its variables, as on a PC. Fedora's shim is signed with both Microsoft's 2011 and 2023 UEFI CAs, so either is enough. Each boot starts from fresh firmware variables.
- **The boot menu is driven over the serial port.** OVMF puts its console on the serial port as well as the screen, and GRUB's menu with it, and reads keys from there. The default entry is left to start when GRUB's 10 seconds run out, which GRUB announces ("Booting \`…'"); another entry is reached with GRUB's one-byte keys `v` and `^` and started with Enter. No entry is edited, so the kernel starts with exactly the arguments in `iso.yaml`, which the checks inside compare.
- **The way in is a systemd credential, not a change to the ISO.** QEMU puts two credentials into the VM's SMBIOS tables, which systemd reads only in a VM: `getty.ttys.serial` makes systemd start a login on the serial port, and `lumen.live-check` holds `live-session.sh`. `boot_iso.py` logs in as root, which the live session leaves without a password, retrying until livesys has unlocked it, and runs the script from `/run/credentials/@system`.
- **What it checks inside:** Secure Boot on (the firmware's `SecureBoot` variable); the kernel arguments; SELinux enforcing with the targeted policy; for "Check this USB", that dracut's `checkisomd5@` service finished; KWin and the Plasma shell running as `liveuser` in an active Wayland session, still there 30 seconds later; then no SELinux denial in the journal or the audit log since boot. It records the time Plasma took, kernel lockdown, the sleep states offered, the Secure Boot certificates and any failed units, without judging them.
- **What it keeps:** each boot's serial log, QEMU's log, and screenshots of the menu and the desktop (or of the screen when a step failed), as the `boot-iso` artifact for 7 days.

## How the install test works

- **The VM** is the boot test's, with an empty 64 GiB disk added (a sparse file) and still no network card, so the installer can only use the ISO's own copy of the image ([ADR 0014](../docs/decisions/0014-install-from-the-iso.md)). It runs twice, keeping its firmware variables, where the installer adds its boot entry.
- **First, from the ISO.** The default entry boots the live session, and `install_iso.py` logs in as root on the serial port. `install-live.sh`, the `lumen.install` credential, checks that the VM has no network, that the ISO's copy of the image is in the live system's container storage under the name the installer's kickstart gives it and is the live system's own build, and adds the test's settings, the `lumen.install-ks` credential, to the end of the installer's kickstart: language, keyboard, time zone, the disk, emptied and laid out by Lumen's install profile without encryption, and a root password. In a live session Anaconda reads no other kickstart.
- **The installer runs as the desktop starts it**, through `liveinst`, but with Anaconda's text interface on the serial port in place of WebUI. Anaconda stops at its summary. The text interface applies a kickstart's disk layout only once someone has gone through the disk's three screens, so the test goes through them, taking and recording the choice the kickstart and Lumen's install profile marked on each. Then it checks that no part is marked `[!]`, left to fill in, and presses `b`. Anaconda's logs stream to the VM's second serial port. Once it says "Installation complete", `install-live.sh report` checks that Anaconda ran `bootc install` from container storage, that SELinux stayed enforcing throughout (Fedora's liveinst switched it to permissive while Anaconda ran; Lumen's live stage removes that, [ADR 0015](../docs/decisions/0015-installer-enforcing.md)), and that no SELinux denial was logged, the installer's included. Then the VM switches itself off.
- **Then, from the disk.** No CD now, and a reboot restarts the VM rather than ending the test, in case shim adds its boot entry first. The test logs in as root with its password, and `installed-system.sh`, the `lumen.installed-check` credential, checks Secure Boot, SELinux enforcing, that `bootc status` and the deployment's origin file say the system follows `ghcr.io/edmundhills/lumen:dev` with signatures checked (`ostree-image-signed`), that it runs the ISO's copy, by digest and version, that its root is Btrfs with `/home` a subvolume of its own, mounted with `compress=zstd:1`, and that `systemd-remount-fs.service` didn't fail ([ADR 0016](../docs/decisions/0016-btrfs-compression.md)). It records `bootc status`, the kernel arguments, `/etc/fstab`, the mounts, the home snapshots unit, kernel lockdown, the sleep states, failed units and SELinux denials, for step 1.9 to judge.
- **What it keeps:** the serial logs and QEMU's logs of both runs, Anaconda's logs (`install-anaconda.log`) and screenshots, in the same `boot-iso` artifact. The disk is deleted unless something failed.
