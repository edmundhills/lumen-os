# 0007. Re-chunk the image with rpm-ostree, against a download budget

- Status: **Accepted** (2026-10-28), after three CI runs on the branch `claude/next-step-zfy63s` (image runs #11 to #13) showed it works. The first `dev` build re-chunked on main is still to come; [Follow-up](#follow-up) records it.
- Deciders: lead engineer (Claude), at step 1.5c, which [ADR 0004](0004-phase-0-review.md) left the choice of tool to. The owner reviews it at the Phase 1 acceptance (step 1.17).

## Context

bootc updates a system by downloading the image layers it doesn't have yet ([risk 14](../risks.md#14-updates-download-too-much)). How much a Lumen update downloads today, measured on 2026-10-28 from the manifests of the four `dev` builds on ghcr.io:

- The image has 262 layers, about 3.0 GiB compressed: Kinoite's 257 and five from Lumen's build.
- A rebuild with no change to the image (`dev-44.20261028` to `.1`, a commit that changed only documents) downloads **113 MiB**. CI builds from scratch, so dnf runs again and writes a new 113 MiB layer with the same packages in it.
- A base bump (`.2` to `.3`, Kinoite 44.20261027.0 to 44.20261028.0) downloads **487 MiB** in 12 layers: 10 of Kinoite's, the dnf layer again, and the small layers after it.
- `.1` to `.2` downloaded **all 3,082 MiB**, with no change to the content. From `.2` on, Podman reused Kinoite's zstd-compressed layers from the copy on ghcr.io instead of compressing them again with gzip, so every layer got a new digest. How layers are compressed is part of what users download.

Three tools re-chunk a bootc image. Checked on 2026-10-28, in their source code where their documentation was silent:

1. **`rpm-ostree compose build-chunked-oci`**, Fedora's documented tool. It reads an image from Podman's storage and writes it again, with each package's files in that package's layer, packed into at most `--max-layers` layers. Since rpm-ostree 2026.2, `--previous-build` takes an earlier build and keeps its packing: each package stays in the layer it was in, and new packages go into a layer kept empty for them. It reads only the earlier build's manifest, where it recorded each layer's packages in the annotation `ostree.components`. It keeps the image's settings and labels (its `config`), and replaces or adds only `ostree.commit`, `ostree.final-diffid`, `ostree.bootable` and `containers.bootc` (rpm-ostree's `compose.rs`, and ostree-ext's `encapsulate.rs` in the bootc repository). Kinoite 44 ships rpm-ostree 2026.3, so it can run from the image itself, at exactly the base's version.
2. **chunkah** (`coreos/chunkah`, 0.7.1), meant to succeed it. It groups files by content, isn't tied to RPM or to bootc, and Fedora's `bootc-base-imagectl rechunk --chunkah` can use it. But it has no option to keep an earlier build's packing, its documentation says packing for bootable images "still needs tuning", it loses the image's labels unless they are passed back in, and Kinoite doesn't ship it, so it would be another image to pin and trust.
3. **`hhd-dev/rechunk`**, the GitHub Action Universal Blue uses. It wraps rpm-ostree's chunking with its own handling of the earlier build, from before rpm-ostree could do either itself. It is a third-party action with an image of its own to pin and trust.

What shaped the design:

- rpm-ostree stops with an error when the earlier build has a layer without `ostree.components`. Builds made by `podman build`, such as today's `dev`, have none, and neither does Kinoite. The first re-chunked build must start a fresh packing.
- rpm-ostree puts every file no package owns in one layer, together with the initramfs. A file marked with the extended attribute `user.component` goes into a layer of its own instead. With Ubuntu's Podman 4.9.3, which the CI runners use, an attribute set in a `RUN` step stays on the file in the image and in its layer (checked on 2026-10-28). The initramfs itself can't be moved this way: rpm-ostree files it under a component of its own before it reads the marks (`container.rs`, which adds it to the paths it skips). Image run #11 showed that a mark on it did nothing.
- `/usr/lib/os-release` belongs to a Fedora package, and Lumen writes its build version into it, so that package's layer, and the other packages packed with it, would change with every build.
- rpm-ostree can write the image to Podman's storage or as an OCI layout, a folder of compressed layers. Pushing from Podman's storage compresses the layers again and may drop their annotations. The OCI layout can be pushed as it is.

What the CI runs found, all on 2026-10-28 with Kinoite 44.20261028.0:

- **Re-chunking changes no file.** Image run #11 compared the built and the re-chunked image, all 470,000 paths: mode, owner, size, link target, attributes and SHA-256. They differ only inside `/sysroot/ostree/repo`, which holds the new ostree commit. The labels and settings are the same, and `check-image.sh` and `bootc container lint` pass on the result.
- **Two builds of the same commit differ in 11 files**, found by building it twice from scratch in run #12: six fontconfig caches, the rpm database (`/usr/share/rpm/rpmdb.sqlite`, 101 MB, owned by `rpm`), dnf's state in `/usr/lib/sysimage/libdnf5` (owned by `libdnf5`), and os-release. The caches alone made the 275 MiB layer of files no package owns, with its 228 MiB initramfs, change on every build. The databases made the layers of `rpm` (34 MiB) and of the nine packages packed with `libdnf5` (23 MiB) change.
- **A rebuild downloads 41 MiB** once those files have a layer of their own (run #13): 32.8 MiB for what every build writes afresh, mostly the rpm database, and 8.1 MiB for the ostree commit. Before that, run #11 measured 338 MiB.
- The re-chunked image has 257 layers, 3.2 GiB compressed. Re-chunking and checking the result take about 13 minutes of each CI run: about 6 for rpm-ostree, and the rest to copy the result into Podman's storage and run the checks. Podman commits each step of the check build slowly on the runners' kernel, which lacks native overlay diffs.

## Decision

1. **The tool is `rpm-ostree compose build-chunked-oci`**, run from the built image itself by `image/rechunk.sh`. It writes an OCI layout with gzip-compressed layers, format version 2 (each layer lists its parent folders, which rpm-ostree's documentation recommends for reproducible layers), and at most 256 layers of packages, as many as Kinoite has.
2. **Each build keeps the packing of the newest build on ghcr.io**, `dev`, read by digest without logging in. While `dev` isn't re-chunked (`image/rechunk.py chunked`), the build packs afresh. That happens once, after this lands.
3. **Files that change on their own get their own layer.** `image/layer_hints.py` marks them with `user.component` in the `lumen` stage: `lumen-build-state` for what the package step writes afresh on every build (the rpm database, dnf's state and fontconfig's caches, 43 files), `lumen-os-release` for os-release, and `lumen-overlay` for every file the overlay adds, so a change to Lumen's defaults doesn't take the shared layer with it. The shared layer then holds the initramfs and files that change only with the base. When the budget catches a new file that changes on every build, it goes on that list.
4. **The re-chunked image is checked before anything uses it.** It must have the same labels and settings as the built image, apart from the new ostree commit, and the base image named in two labels, `org.opencontainers.image.base.name` and `.base.digest`, which Podman wrote as manifest annotations and re-chunking would otherwise drop. It must also pass `image/check-image.sh` and `bootc container lint` again.
5. **skopeo pushes the OCI layout unchanged** (`--preserve-digests`), so the digest CI measured and checked is the digest users get, and step 1.6 signs.
6. **Every CI run measures the update** from `dev` to the new build: the layers `dev` lacks, by size and the packages in them, on the run's summary page. Until there is a `stable` channel, `dev` is what users have; step 9.2 moves the comparison to `stable`.
7. **The download budget applies to builds on the same base image.** A build whose update from `dev` downloads more than `DOWNLOAD_BUDGET_MIB` (in `.github/workflows/build-image.yml`) fails, on pull requests as on `main`. When the base image changed, the size is reported but not held to the budget, because it is mostly Fedora's updates; the base workflow's weekly pull request shows it. The budget is **100 MiB**: the 41 MiB of a rebuild, plus room for a normal change. A change that needs more, such as new packages that weigh more than that, raises it in the same pull request and says why.

## Consequences

- An update on the same base downloads the 41 MiB every build writes, plus the layers of the packages and overlay files that changed. Before re-chunking, an update with no change downloaded 113 MiB.
- Most of the 41 MiB is the rpm database, which CI writes afresh because it builds from scratch. Reusing the `base` stage between CI runs when neither the pin nor `packages.toml` changed would keep it the same, and leave about 8 MiB.
- The first `dev` build after this lands downloads in full once, because none of its layers match the previous build's.
- Each CI run takes about 13 minutes longer: the check job now takes about 40.
- The layers are gzip, not zstd as Kinoite's are, so Lumen's image doesn't share layers with Kinoite on ghcr.io. Users never had Kinoite's layers, so they download nothing more for it.
- A Fedora release upgrade or a change of rpm-ostree's packing still moves most packages, and that update is large. Raising `--max-layers` also starts a fresh packing.
- If rpm-ostree changes the labels it writes, the check fails and names the label, and someone decides whether to accept it (`ADDED` in `image/rechunk.py`).
- **Revisit** when Kinoite ships chunkah, or chunkah learns to keep an earlier build's packing, since Fedora is moving to it ([risk register, watch list](../risks.md#watch-list)).

## Follow-up

- 2026-10-28: the push path is untested until the branch reaches main, because only builds of main push. The first re-chunked `dev` downloads in full once and isn't held to the budget; the second shows the real size of an update. Step 1.6 records both here.
- 2026-10-29 (step 1.6): the owner merged the branch, rebased with their sign-off, and main's image run for `02d400d` was green in 52 minutes. It pushed the OCI layout as it was, as `dev-44.20261029` (`sha256:101c706b…181c`), and `ghcr.io/edmundhills/lumen:dev` now has 257 layers: the ostree commit first, with no annotation, then 256 whose `ostree.components` name their packages, the last of them the empty one kept for new packages. `rechunk.py chunked` accepts it, so the next build keeps its packing. The labels are all there, among them the build version and the two naming the base. As expected, the update from the last build that wasn't re-chunked (`dev-44.20261028.3`, on the same base) downloads 256 of the 257 layers, 3,183.6 MiB, once. The next build on main is the first held to the budget.
- 2026-10-29 (step 1.6): that next build (`929376e`) failed at re-chunking, before it pushed anything. rpm-ostree reads the earlier build through containers/image inside the image it re-chunks, and that image now has Lumen's trust policy (ADR 0008), which refuses Lumen's own images unsigned: `OpenImageOptional: A signature was required, but no signature exists`. The layer plan is all rpm-ostree reads from the earlier build, and nothing in it is trusted. So `rechunk.sh` now reads the manifest and config of a build on a registry itself, with `skopeo inspect`, which checks no signatures. It hands rpm-ostree an OCI layout of just those two (`rechunk.py layout`), which the policy allows like any local image. Checked in WSL: the image's own skopeo reads the layout made from today's `dev` as `sha256:101c706b…181c`, with its 257 layers.
- 2026-10-29: with that fix, main's next run (`2a7107c`) re-chunked with `dev`'s layer plan. Its update from `dev` would download **336.5 MiB in 7 layers**, over the budget: the 274.6 MiB layer with the initramfs and the files no package owns, the 32.8 MiB of build state, `python3-libs` (18.3 MiB), the ostree commit and three small ones. **The budget had never been enforced:** GitHub runs a step with `bash -e` unless the workflow names its shell, so `rechunk.py download … | tee` passed whatever the check said. The workflows now name `bash`, which runs each step with `pipefail`. Which files changed in those layers wasn't measured: the build that changed them wasn't pushed. This commit added the trust policy and its folder, new image checks and new Python imports. Python writes a bytecode file for any module it imports that has none, a file no package owns, so the build now runs Python with `PYTHONDONTWRITEBYTECODE=1`. Those changes alter the image once, so the update from this one `dev` (`DOWNLOAD_BUDGET_EXEMPT`, by digest) isn't held to the budget; the next build is. If it goes over, compare the changed layers' file lists with the previous build's.
- 2026-10-29: main's run for `5ca3439` (`44.20261029.1`), exempted, measured **315.5 MiB in 5 layers**: the shared layer (274.6 MiB), the build state (32.8), the ostree commit (8.1), the overlay and os-release. `python3-libs` and the other package layers no longer changed, so the bytecode files the build's Python wrote had been changing them. Whether the shared layer now stays the same between builds is the next build's to show: it is the first held to the 100 MiB budget, with `pipefail`, against this `dev`.
- 2026-10-29: the first build held to the budget against `44.20261029.1` was the cloud session's check run #19, for `4c16994` on the branch `ccr-aa9986c4-vir9s7`, which removed the exemption outright (main empties it instead; the effect is the same). Its update from `dev` downloads **40.8 MiB in 3 of 257 layers**, within the 100 MiB budget: 32.8 MiB of build state, the 8.1 MiB ostree commit, and os-release. The shared layer with the initramfs didn't change, so a rebuild downloads what run #13 measured.
- 2026-10-29: main's first build held to the budget, image run #22 for `169d2f5`, built `44.20261029.2` (`sha256:65d764db…87df5`) in 49 minutes. Its update from `44.20261029.1` downloads **40.9 MiB in 3 of 257 layers**, as check run #19 measured: the build state (32.8 MiB), the ostree commit (8.1) and os-release. It was signed, and `dev` moved to it.
- 2026-10-30 (step 1.8b-3b): the build of `2b2c738`, which added Lumen's tuned profiles to the overlay ([ADR 0013](0013-tuned-profiles.md)), went over the budget against `44.20261030.3` and wasn't pushed: **315.5 MiB in 5 layers**, the shared layer (274.6 MiB), the build state, the ostree commit, the overlay and os-release. Its packages were exactly those of the build before, and its new files are all marked `lumen-overlay`, so what changed the shared layer is most likely the four new folders `/usr/lib/tuned/profiles/lumen-*`, which no package owns. Layers of format version 2 list the folders of their files, and a folder can't be marked without taking the packages' files in it along (`layer_hints.py`). The trust policy's new folder at step 1.6 gave the same 315.5 MiB. New folders in the overlay therefore cost one download of the shared layer; the update from `44.20261030.3` is exempt (`DOWNLOAD_BUDGET_EXEMPT`), and the next build shows whether it is back to 41 MiB.
