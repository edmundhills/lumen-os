# 0011. Make the disk images with osbuild's image-builder, which bootc-image-builder became

- Status: **Accepted** (2026-10-29), at step 1.8a, for the qcow2. Which tool turns the live stage into the install ISO is step 1.8b's to decide, by trying both candidates ([Consequences](#consequences)).
- Deciders: lead engineer (Claude). The owner reviews this at the Phase 1 acceptance (step 1.17).

## Context

The spec builds the qcow2 for the tests "with bootc-image-builder", and the install ISO as a live ISO built from the image, trying Universal Blue's Titanoboa first (ADR 0002). What those tools are now, checked on 2026-10-29 in their source code at the commits named, in their container images, and by running them:

- **bootc-image-builder is now part of image-builder.** On 2026-10-01 its repository (`osbuild/bootc-image-builder`) deleted its sources: they moved into osbuild's `image-builder` (`osbuild/image-builder`, the former `image-builder-cli`). The old container, `quay.io/centos-bootc/bootc-image-builder`, is now CentOS Stream 10 with the `image-builder` RPM (85.0.0, osbuild 193 in the build of 2026-10-26), linked as `bootc-image-builder` so that the old command line still works. Upstream's migration guide says new workflows should use `image-builder build --bootc-ref <image> <type>` directly, from the host's RPM or from the container `ghcr.io/osbuild/image-builder-cli`. That container is Fedora 44 with image-builder and osbuild, tagged by release (`v78.0.0` to `v88.0.0` so far, about one a week); `v88.0.0` was built on 2026-10-27.
- **What image-builder reads from a bootc image.** It reads os-release and needs `ID`, `VERSION_ID` and `NAME`. It knows the IDs `fedora`, `centos`, `rhel` and `ol`; for any other, such as `lumen`, it logs "Unknown distro" and uses a generic runner, which for a disk image changes nothing, because the build runs inside the image itself. It names the distro `bootc-<ID>-<VERSION_ID>`, which must read as a name and a version with at most one dot: Lumen's `VERSION_ID=0.1` reads as 0.1, but a version such as `0.1.1` would stop the build. The root filesystem's type comes from the image's `disk.yaml` if it has one, else `--bootc-default-fs`, else bootc's own install config (Lumen's `20-lumen.toml` says Btrfs). Its own settings, if any, are in `/usr/lib/image-builder/bootc/` (or the old `/usr/lib/bootc-image-builder/`).
- **How it installs the image.** For a qcow2, osbuild's `org.osbuild.bootc.install-to-filesystem` stage runs the image's own bootc: `bootc install to-filesystem --source-imgref <the image in containers-storage> --skip-fetch-check --generic-image --target-imgref <name>`, where the name is the one image-builder was given (`raw_bootc.go`). That name is what the installed system updates from, and bootc reads its install config from the image. By default image-builder adds the kernel arguments `rw console=tty0 console=ttyS0`. Its default partition table for x86_64 is a 1 MiB BIOS boot partition, a 501 MiB EFI system partition, a 1 GiB `/boot` and the root, which it sizes to twice the image.
- **What a qcow2 of Lumen holds**, built in WSL from `dev` `44.20261029.1` with image-builder 88.0.0 and checked with `image/check-disk.sh`:
  - bootc said "Installing image: ostree-image-signed:docker://ghcr.io/edmundhills/lumen:dev", and the deployment's origin file says the same. So Lumen's `enforce-container-sigpolicy = true` reaches installs that image-builder makes, as ADR 0008 inferred.
  - GPT, with the partitions above: FAT (label `EFI-SYSTEM`), ext4 (`boot`), and Btrfs (`root`) on a partition typed as an x86-64 root. The Btrfs filesystem holds one subvolume, `root`, with the deployment in it. The stateroot's `/var` holds only `cache`, `lib`, `log` and `tmp`: `/var/home` comes on the first boot, as a plain folder, so `lumen-home-snapshots` will find no subvolume there and say so.
  - osbuild mounted the root with `compress=zstd:1` for the install, so the files are stored compressed, and wrote a mount unit for `/` in the deployment's `/etc` with `subvol=root,compress=zstd:1,ro`. The kernel command line says only `rootflags=subvol=/root`, so whether files written after boot are compressed is the boot test's to read from `/proc/mounts`.
  - The EFI system partition has shim as the fallback loader (`EFI/BOOT/BOOTX64.EFI`) and Fedora's shim, GRUB and menu, from bootupd. `/boot` has one entry, "Lumen OS 0.1 (ostree:0)", with the kernel and initramfs it names.
  - The qcow2 is 3.6 GiB (15.5 GiB virtual); the raw copy for the check uses 5.3 GiB. The build took 48 minutes in WSL, 29 of them copying the image's files, through its 257 layers, into osbuild's build root; bootc's own install took 14.
- **Titanoboa is now a small packer.** Since 2026-05-19 (commit `5c457c3`, "Only use container images as the only source of truth"), Titanoboa takes a container that already holds the whole live system and packs it into an ISO: a squashfs of its files, the kernel and initramfs, the EFI files, a GRUB menu from `iso.yaml`, and `xorriso`. It follows the "container-native ISO contract v0.1.0", which osbuild's developers wrote and which image-builder's `generic-iso` type implements too. Titanoboa has no releases (projects pin a commit), runs `dnf` in an unpinned `quay.io/fedora/fedora:latest` to get its tools, and makes an ISO that boots only on UEFI. image-builder's `generic-iso` also boots on BIOS, checks the medium with `implantisomd5`, and can copy the image to install into the live system's container storage (`--bootc-installer-payload-ref`), so the installer needs no network. In both, the live session, Anaconda and the boot files are the container's job, so the `live` stage is the same whichever tool packs it.
- **The fallback in ADR 0002 has shrunk.** image-builder dropped bootc-image-builder's `anaconda-iso` type; only the old command line in the CentOS container still has it. Its `bootc-installer` type is still there but discouraged in favour of `generic-iso`.

## Decision

1. **image-builder makes the qcow2**, from the container `ghcr.io/osbuild/image-builder-cli`, pinned by release and digest in `.github/workflows/build-image.yml`, with image-builder's own command line: `image-builder build --bootc-ref <image> qcow2`. It is the tool bootc-image-builder became, the way upstream asks new workflows to use it, on the same Fedora release as Lumen, with releases a pin can follow. The spec's "bootc-image-builder" is read as this tool.
2. **Every build gets a qcow2**, in the image workflow's build job, after re-chunking and before anything is pushed: the boot test (step 1.9) needs one for every push and pull request ([architecture 9.9](../architecture.md#99-where-each-test-layer-runs)). It is made from the re-chunked image, which is what users get, named `ghcr.io/<owner>/lumen:dev`, so that the installed system follows `dev` as a Lumen system would. It isn't uploaded, because the boot test will run in the same job.
3. **`image/check-disk.sh` checks every qcow2**, read-only, before the job goes on: a GPT disk with an EFI system partition, a `/boot` and a Btrfs root; shim and GRUB on the EFI system partition; one boot entry for one ostree deployment; that deployment recorded as `ghcr.io/<owner>/lumen:dev` with the signed transport; and its os-release saying Lumen and the build's version. `image/disk.py` holds the checks, with unit tests.
4. **Keep `VERSION_ID` to at most one dot**, or image-builder can't make disks of the image. `os-release.sh` checks it.

## Consequences

- The build job takes longer and needs room for the disk next to the image: the qcow2, osbuild's copy of the image and the raw copy for the check, about 20 GB more at the peak. How much longer comes with the first run in CI; WSL's 48 minutes are mostly its slow disk. If it is too slow, a later step can make the qcow2 in a job of its own, which needs the image handed over.
- image-builder is pinned like the bases: a new release needs a pull request that moves the pin. Renovate is planned for the pinned tool images (architecture 9.8, step 9.2); until then, move it by hand when a release fixes something Lumen needs.
- Step 1.8b builds the `live` stage to the container-native ISO contract and packs it with Titanoboa first, as the spec asks, and with image-builder's `generic-iso`; it records which one Lumen keeps, and why, in a follow-up here or an ADR of its own.
- Step 1.8c installs with Anaconda's `bootc` kickstart command from the copy of the image on the ISO, which also runs `bootc install to-filesystem`, so the same install config applies. Bazzite's live ISO uses `ostreecontainer --transport=containers-storage` instead and then rewrites the origin file to the signed transport by hand, which Lumen doesn't need if `bootc` works. image-builder's documentation warns that a bootc system installed through Anaconda fails to start `systemd-remount-fs.service` (Fedora's atomic-desktops tracker, issue 72; Red Hat bug 2332319); the boot test's `systemctl --failed` would catch it.
- If no live ISO works, ADR 0002's fallback, `anaconda-iso`, exists only in the deprecated command line. `generic-iso` with a plain Anaconda environment and no live desktop would be the nearer fallback; either needs the owner's approval, as ADR 0002 says.

## Follow-up

- 2026-10-29: the first run in CI, main's image run for `c624303`, built `44.20261029.4` and was green, signing included. On the runner, "Make the qcow2" took 11 minutes 19 seconds, about 4 of them osbuild copying the image, and "Check the qcow2" 25 seconds, so the build job took 55 minutes, against 45 to 52 before. `df` showed 123 GB free after the cleanup, 115 GB after the build, 104 GB after re-chunking and 99 GB after the qcow2, so disk is no concern yet. The qcow2 is 3.65 GiB, with a 14 GiB root. `check-disk.sh` found what it found in WSL: the four partitions, shim and GRUB, one entry ("Lumen OS 0.1 (ostree:0)"), the root mounted with `subvol=root,compress=zstd:1,ro`, and a deployment that follows `ostree-image-signed:docker://ghcr.io/edmundhills/lumen:dev`. The update from `44.20261029.3` downloads 40.8 MiB, within the budget (ADR 0007).
- 2026-10-29: step 1.8b-2 chose image-builder's `generic-iso` for the install ISO, with an SELinux stage Lumen adds to its build ([ADR 0012](0012-install-iso.md)).
