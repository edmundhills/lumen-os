# 0014. Install the ISO's own copy of the image with Anaconda's bootc command

- Status: **Accepted** (2026-10-30), at step 1.8c.
- Deciders: lead engineer (Claude). The owner reviews it at the Phase 1 acceptance (step 1.17), and is asked about one point now (Consequences).

## Context

The install ISO boots a Lumen live session ([ADR 0012](0012-install-iso.md)), whose installer must put Lumen on the disk with no network, so that download speed can't make the install slow (spec: under 10 minutes). The installed system must then follow `ghcr.io/edmundhills/lumen:dev` and check Lumen's signature from its first update ([ADR 0008](0008-image-signing.md)). What the tools do, read in their source on 2026-10-30:

- **Anaconda's `bootc` kickstart command** (pykickstart's `F43_Bootc`, at `1568c86`) takes `--source-imgref` with a transport, `--target-imgref` without one, and `--stateroot`, which defaults to `default`. Anaconda 44.35's `DeployBootcTask` (`pyanaconda/modules/payloads/payload/rpm_ostree/installation.py`, unchanged since 44.30 except for an unrelated fix) runs `bootc install to-filesystem --bootloader=grub --karg=… --stateroot=… --source-imgref=… --target-imgref=…` on the mounted target, after emptying it. It accepts only `/`, `/boot`, `/boot/efi`, `/home` and `/var` as mount points, and empties the disk's root first: it unmounts the others there and deletes their folders. Afterwards `PrepareBootcMountTargetsTask` binds `/var` into the system from that root if `/var` is a mount point of its own, but nothing makes the folder again, so the install stops (seen in CI on 2026-10-31, Follow-up). Nothing binds `/home`. Its kernel arguments include a kickstart's `bootloader --append`.
- **In a live session Anaconda reads one kickstart**, `/usr/share/anaconda/interactive-defaults.ks`: with `--liveinst`, `find_kickstart` ignores any kickstart given on the command line or on a disk labelled `OEMDRV`. A `bootc` command there picks Anaconda's `RPM_OSTREE` payload with a bootc source, ahead of copying the live system (`PayloadFactory.get_type_for_kickstart`). Anaconda's own copy of the file has no commands and is marked deprecated, with nothing in Anaconda's configuration files to replace it for this. Anaconda WebUI (releases 88 to 90) treats every payload but DNF alike: it hides the software selection.
- **bootc 1.17.1, run from the live system**, reads its install settings from the running system (`/usr/lib/bootc/install/*.toml`), which is the Lumen image, so Lumen's `enforce-container-sigpolicy = true` applies and the target is recorded as `ostree-image-signed:docker://<target>`. The source passes the trust policy because Lumen's `policy.json` accepts the `containers-storage` transport. Without `/ostree/repo`, which the live stage removes (ADR 0012), bootc reads whether the system has SELinux from `/etc/selinux/config`. When it lacks the right to write labels the policy doesn't know (`mac_admin`), it runs itself again with `/usr/bin/ostree`'s label, which gives it `install_t`.
- **image-builder 88's `--bootc-installer-payload-ref`** adds an `org.osbuild.skopeo` stage at the end of `generic-iso`'s `os-tree` pipeline, which copies an image from the build machine's container storage into the tree's `/var/lib/containers/storage`, under the name given (`pkg/manifest/os_from_container.go`, osbuild's `stages/org.osbuild.skopeo`). The SELinux stage Lumen adds after it labels those files too.
- **A copy out of container storage gets a new manifest.** containers/image's storage source offers each layer uncompressed, so a copy from container storage rewrites the manifest's layer list, and the copy's manifest digest differs from the build's on ghcr.io. The configuration, and with it the image ID, stays the same. A copy that must rewrite the manifest is refused while the image has signatures stored, "Would invalidate signatures" (`image/storage/storage_src.go` and `image/copy/single.go` in containers/container-libs, `8785764`). `podman pull` stores the sigstore signatures it checked.
- **The live session's root is an overlay file system.** On one, Podman's storage library can use its overlay driver only through `fuse-overlayfs`, which it then picks by itself (containers/storage `drivers/overlay/overlay.go`). The Lumen image has `fuse-overlayfs`, from Kinoite (the package names in `dev`'s layers).
- **liveinst switches SELinux to permissive while Anaconda runs.** Fedora's `liveinst`, which the live desktop's installer icon starts, runs `setenforce 0` before Anaconda and sets the old mode back afterwards. It has done so since at least 2010 (`data/liveinst/liveinst` in Anaconda's history). The installed system is enforcing either way.
- **Other ways, not taken:** Bazzite's live ISO installs with `ostreecontainer --transport=containers-storage` and rewrites the origin file to the signed transport in `%post`, because Anaconda's `ostreecontainer` ignores bootc's install settings (ADR 0008). image-builder's own `bootc-installer` image type makes an Anaconda boot ISO with no live session, which ADR 0002 keeps as the fallback only.

## Decision

1. **The installer's kickstart is `installer/anaconda/interactive-defaults.ks`**, which the live stage installs in place of Anaconda's. It has one command:

   `bootc --source-imgref=containers-storage:ghcr.io/edmundhills/lumen:dev --target-imgref=ghcr.io/edmundhills/lumen:dev`

   The name in the container storage is the name the system then follows, so one name serves both, and `image/iso.py install-image` reads it from the kickstart for the workflow and the checks.
2. **The ISO carries the build its live system is made from.** The `iso` workflow copies the build by digest into root's container storage with `skopeo copy --remove-signatures`, which checks its signature with Lumen's trust policy first (ADR 0012) and then keeps no signatures, so image-builder may copy it again. It names the build as the kickstart does, and `image/make-iso.sh` passes it to image-builder with `--bootc-installer-payload-ref`. From there on the build is known by its image ID, which no copy changes.
3. **Checks:**
   - `image/live/check-live.sh`: the kickstart is installed, the parser Anaconda uses (pykickstart) reads a `bootc` command from it that installs from container storage under the name it then follows, no other source is set, `bootc install print-configuration` run in the live system says `enforce-container-sigpolicy`, and `bootc`, `skopeo` and `fuse-overlayfs` are there.
   - `image/check-iso.sh`: the squashfs has the kickstart, and its container storage holds the image the kickstart names, with the signed build's image ID, the same digest in its manifest and in its stored configuration, the build's version, and all its layers (`image/iso.py payload`).
   - **The install test** (`tests/boot/install_iso.py`, in the `boot-iso` workflow after the boot test) installs from the ISO onto an empty 64 GiB disk in the VM the boot test uses, which has no network card, then starts the installed system with Secure Boot and checks it: SELinux enforcing, `bootc status` and the origin file say it follows the kickstart's name with signatures checked, it runs the ISO's copy (the digest the live system's storage gives it, and its version), and its root is Btrfs with `/home` a subvolume of its own. It records `bootc status`, the kernel arguments, the mounts, the Btrfs compression in use, the home snapshots unit, kernel lockdown, the sleep states, failed units and SELinux denials, without judging them; step 1.9 judges those.
4. **Lumen's install profile has no `/var` subvolume.** `installer/anaconda/lumen.conf` lays out `/` and `/home` only; Kinoite's profile, which it was copied from at step 1.4, also had `/var`, which Anaconda's bootc install can't bind. bootc keeps `/var` in the system's own state folder, as in image-builder's qcow2. `check-live.sh` fails if `/var` comes back. `/home` stays a subvolume of its own for snapper.
5. **How the test drives the installer.** It runs `liveinst`, as the desktop does, with Anaconda's text interface in place of WebUI (`LIVECMD='anaconda --liveinst --text'`), so it goes through the same launcher, kickstart and payload as a person does. Because Anaconda in a live session reads only the installer's kickstart, the test adds its own settings to the end of that file in the VM, after the `bootc` line, which it leaves alone: the language, the keyboard, the time zone, the VM's disk, emptied and laid out by Lumen's install profile (`autopart`, without encryption), and a root password. Anaconda then stops at its summary. In a live session its text interface applies a kickstart's partitioning only once someone has gone through the disk's screens (Installation Destination, Partitioning Options, Partition Scheme Options), so the test goes through them, taking the choice the kickstart and the profile marked on each and recording it. Then it checks that nothing is left to fill in and presses `b`. The keyboard is given whole, console keymap and X layouts: with half of it, Anaconda in a live session asks the live desktop for the rest, through the user pkexec started it as, which a root shell doesn't have. Anaconda's logs go to the VM's second serial port, which the test keeps.

## Consequences

- Installing needs no network, and the installed system checks Lumen's signature from its first update, with no `%post` fix-up.
- **The installed system's first update most likely downloads every layer once.** It records the manifest digest of the ISO's copy, whose layers are listed uncompressed, not those of the build on ghcr.io, so ostree finds none of the layers it already has when it compares. Updates after that are as small as ADR 0007 makes them. The `iso` run's summary gives the build's digest and the install test the installed system's; the update test (step 10.2, or 1.17 by hand) should measure the first update. If it costs too much, the ISO can carry the build as an OCI layout instead, as Fedora's own atomic ISOs do, which keeps its manifest and digest but adds about 3 GB of compressed layers that the squashfs can't share with the live system.
- The ISO carries the image twice: as the live system, and as the copy in its container storage. The squashfs stores identical files once, so it grows by less than the image's size; the first run measures it (Follow-up).
- Each release channel (step 10.1) needs its own name in the kickstart, which the `iso` workflow reads from there.
- **For step 6.10:** a user the installer itself creates gets a home folder made under the system's own `/var/home` during the install, which the `/home` subvolume then covers at boot, if Anaconda's file system table mounts it there. Users made on the first boot (Plasma Setup, then Welcome at step 6.5) don't have that problem. The install test creates no user, so 6.10 must check this when WebUI's account screen is decided. The `/var` bind failure is Anaconda's bug and worth reporting upstream; that is the owner's call, since it means posting to their tracker.
- The test covers what the install does, not WebUI's screens or encryption: the owner's install at step 1.17 covers both, and steps 6.6 and 6.10 add them to CI.
- **For the owner:** Fedora's `liveinst` runs the installer with SELinux permissive in the live session, as on every Fedora live ISO. Lumen doesn't add this, and the installed system is enforcing, but it weakens the live session's choice of enforcing (ADR 0012) while the installer runs. Options: (a) keep Fedora's behaviour; (b) once the install test passes, try the installer enforcing in CI, with a small change to `liveinst`, and keep that if it installs with no denials. Recommended: (b), as its own step, with an ADR. **The owner chose (b)** on 2026-10-31: step 1.8d.

## Follow-up

- 2026-10-31, the first runs in CI, all on `dev` `44.20261030.4` (digest `1064a35a…`, image ID `4581cfbc…`), from the branch `claude/progress-next-step-cvyy8f`:
  - `iso` run 41145452388 made the ISO with the copy: the live stage's check passed 13 of 13 and "Check the ISO" 7 of 7, the copy's files labelled like the rest. The ISO is 3,831,488,512 bytes (3.57 GiB) against 3.19 GiB before: the copy adds 0.38 GiB, because the squashfs stores the files it shares with the live system once. In the live session Podman read the copy, through fuse-overlayfs, as build `44.20261030.4` with the manifest digest `f473b777…`, rewritten as Decision 2 expects.
  - The install test then needed four fixes of its own before Anaconda got past its start and its summary (a check-title bug, a whole keyboard setting, the disk's screens, and showing Anaconda's error report), and found Anaconda 44.30's `/var` bug (Context), fixed in the profile (Decision 4).
  - `iso` run 41197163008 made the ISO with that profile. On it, the install test installed Lumen with no network in about 7.5 minutes, Anaconda running `bootc install to-filesystem --bootloader=grub --stateroot=default --source-imgref=containers-storage:ghcr.io/edmundhills/lumen:dev --target-imgref=ghcr.io/edmundhills/lumen:dev /mnt/sysimage`. bootupd put shim and GRUB in place and `efibootmgr` added a boot entry labelled "Fedora", first in the boot order. liveinst switched SELinux to permissive and back, and no denial was logged. The installed system started from the disk with Secure Boot to a login in 21 seconds, with SELinux enforcing and no denials; `bootc status` and the origin file say it follows `ghcr.io/edmundhills/lumen:dev` with `containerPolicy`, `ostree-image-signed`, and it runs the ISO's copy. `/var/home` is the `/home` subvolume, and the home snapshots unit succeeded.
  - **Not yet right:** the running system mounts its Btrfs without compression. Anaconda mounts it with `compress=zstd:1` while installing, but bootc's kernel arguments give only `rootflags=subvol=/root`, and the `/` line in Anaconda's `/etc/fstab` can't be applied to the composefs root, so `systemd-remount-fs.service` fails, as ADR 0011 warned. Step 1.8e fixes both; until then the install test records the compression rather than failing on it. `mcelog.service` failed too, on the runner's CPU, as in the live session.
